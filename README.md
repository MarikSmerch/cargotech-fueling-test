# Задание 1. Противоречия

| № | Расхождение | Решение и причина |
|---|---|---|
| 1 | В разговоре и макете лимит на рейс — 20 000 ₽, в API — 15 000 ₽. | Брать общий лимит из `getTrip()`, а не из макета: в приложении должны быть актуальные данные API. |
| 2 | На макете доступно 12 450 ₽, в API изначально 9 340 ₽. | Показывать `limitLeft` из API и обновлять его после заправки, не фиксировать сумму в HTML. |
| 3 | Диспетчер советует залить 150 л на «Колесе», хотя доступных 9 340 ₽ на такой объём по указанной в разговоре цене не хватит. | Рассчитывать максимум литров по цене, доступному лимиту и ограничениям АЗС. Не давать оформить заказ, который заведомо не пройдёт. |
| 4 | На «Колесе» колонки обозначены буквами, а API принимает числа. | Показывать для этой сети буквенные обозначения, а в API передавать номера. Соответствие после «Г» считать допущением и уточнить у владельцев данных. |
| 5 | По словам диспетчера, отменить можно до заполнения половины объёма; API запрещает отмену сразу после начала налива. | Разрешать отмену только до начала налива. Если статус успел измениться, показывать причину отказа, а не обещать недоступное действие. |
| 6 | Диспетчер говорит о 40 секундах на установку пистолета; API использует другую модель ожидания и тайм-аут 60 секунд. | Показывать прошедшее время ожидания без обратного отсчёта от неподтверждённых 40 секунд. Переключать состояние только по API. |
| 7 | На итоговом экране написано «Чек отправлен диспетчеру», но по разговору чек приходит позже; API отправку не подтверждает. | Убрать сообщение об отправке. Указать, что чек можно получить позже через диспетчера. |
| 8 | В разговоре старый холд может висеть около суток, а API снимает блокировку при завершении или отмене моделируемой операции. | Не обещать срок возврата и не показывать выдуманные суммы холдов. Выводить доступный остаток и пояснение, что подробности можно уточнить у диспетчера. |
| 9 | Диспетчер объясняет остаток прошлой заправкой и холдом, а в исходном состоянии API история операций пуста и детализации остатка нет. | Не создавать фиктивную историю. Показывать доступный лимит и краткую подсказку о возможных списаниях и блокировках. |
| 10 | В макете указан номер прицепа, но `getTrip()` возвращает только номер тягача. | Показывать только полученный из API номер тягача. Номер прицепа из макета не подставлять: он может меняться. |
| 11 | Диспетчер говорит, что «Волга-Топливо» под Казанью дешевле на 1 ₽/л, но в API цены зависят от конкретной АЗС и могут измениться. | Сравнивать текущие цены выбранных АЗС, а не обещать фиксированную разницу в 1 ₽/л. |

## Задание 2. Рабочий прототип

Приложение запускается в браузере без сборки. Сначала подключается неизменённый `fake-api.js`, затем `app.js`.

Запуск из папки проекта:

```bash
python -m http.server 8000
```

Адрес: `http://localhost:8000`. Также можно открыть `index.html` напрямую, но через локальный сервер надёжнее работает сохранение состояния в браузере.

Сценарий: текущий рейс и остаток → ближайшие АЗС с дизелем → топливо и доступная колонка → объём и сумма → подтверждение → ожидание / налив → результат. Расстояния рассчитаны по прямой, не по дорожному маршруту. Для повторной заправки (например, рефрижератора) после результата можно снова начать заказ из общего лимита.

Особенности реализации:

- `getTrip()` используется для лимита и рейса; старые операции не выдумываются, информацию о возможных блокировках предлагается уточнять у диспетчера.
- `getStations()` загружает краткий список; подробные данные об одной АЗС получаются через `getStation(id)`. Список сортируется по расстоянию или цене, список сортируется по расстоянию, без произвольного ограничения радиуса.
- Водитель выбирает топливо и свободную совместимую колонку. У «Колеса» видны буквенные обозначения, а в API отправляется числовой номер. Обозначения после Г приняты условно.
- Максимальный объём учитывает цену за литр, `limitLeft`, `litersMin` и `litersMax`. Можно ввести объём с точностью до 0,01 л.
- При `PRICE_CHANGED` заказ не оформляется автоматически: показывается новая цена и требуется повторное подтверждение. Обрабатываются `PUMP_BUSY`, `FUEL_NOT_AVAILABLE`, `LIMIT_EXCEEDED` и другие ошибки API.
- Перед отправкой `startFueling()` приложение сохраняет запрос и его `clientRequestId` в `localStorage`. При неопределённом результате сначала проверяется существующая активная заправка через `getActiveFueling()` (без создания нового заказа). Если активного заказа нет, повторная отправка тех же данных и `clientRequestId` возможна только по отдельному нажатию водителя: она либо вернёт уже созданный заказ, либо создаст заказ, если первый запрос не дошёл. После перезагрузки вкладки сохранённые данные используются для восстановления.
- Пока запрос обрабатывается, повторная отправка недоступна. Статус читается через `getFueling(id)`; при обрыве связи приложение не считает заказ отменённым.
- Отменить можно лишь до начала налива. Время ожидания показано без неподтверждённого дедлайна; решение о тайм-ауте принимает API.
- В результате показываются фактические литры, расход и возврат неиспользованной части резерва. Статус отправки чека не выдумывается.

Для повторного тестирования сценариев в консоли браузера:

```javascript
FakeApi.reset();
localStorage.removeItem('cargotech.fueling.client.v1');
location.reload();
```

Для проверки штатного сценария без случайных сетевых ошибок (в консоли после загрузки):

```javascript
FakeApi.config.networkErrors = false;
```

Ограничение на код: `index.html` и `app.js` суммарно менее 60 КБ. Внешних библиотек и фреймворков нет. Наличие старой истории заправок и отправка чеков не имитируются.

Ограничения прототипа: расстояние — по прямой, без учёта дорог и маршрута; буквенное обозначение колонок «Колеса» после Г — допущение, требующее справочника конкретной АЗС. В предоставленном API нет метода поиска заказа по `clientRequestId`, поэтому автоматическое различение «первый запрос не дошёл» и «заказ успел завершиться» невозможно без повторной отправки с тем же идентификатором. Операция подтверждается водителем явно.
